# WaveHub 架构与技术选型

> 目标：一个「音乐版 B 站」——用户上传音频作品，网页端提供音乐编辑器和音乐可视化播放页。
> 原则：**单体优先、边学边做、每个选型都说清楚为什么。**

---

## 0. 总体形态：单体（Monolith），不是微服务

**选择：一个 Go 进程 + 一个数据库 + 一个 Redis + 一个对象存储。**

为什么不学 B 站那样上微服务（B 站开源的 Kratos 框架就是微服务框架）：

| | 单体 | 微服务 |
|---|---|---|
| 学习曲线 | 只需 Go + Gin + SQL | 额外要 gRPC、服务发现、链路追踪、K8s |
| 调试 | 一个进程打断点 | 跨进程排查，日志分散 |
| 部署 | 一个二进制文件扔上服务器 | 需要编排系统 |
| 何时需要 | 一直到日活几十万都够 | 团队 > 20 人、模块需独立扩容时 |

Go 编译出来是**单个静态二进制**，单体部署极其舒服——这正是 Go 相对 Java/Python 的核心优势之一。
微服务解决的是「组织问题」（多团队并行开发），不是「性能问题」。一个人学习期用微服务是纯负担。

代码内部仍然按模块分层（见第 6 节目录结构），将来真要拆微服务时，按目录切出去即可。

---

## 1. Web 框架：Gin

**候选：Gin / Echo / Fiber / chi / 标准库 net/http**

| 框架 | 底层 | 生态 | 中文资料 | 备注 |
|---|---|---|---|---|
| **Gin** ✅ | net/http | 最大 | 最多 | 事实标准，80k+ star |
| Echo | net/http | 大 | 中等 | 与 Gin 能力几乎等价 |
| Fiber | **fasthttp** | 中 | 少 | 快，但不兼容 net/http 生态 |
| chi | net/http | 中 | 少 | 极简路由，适合已经很熟 Go 的人 |
| 纯标准库 | - | - | - | Go 1.22 后路由已够用，但要自己造中间件轮子 |

**为什么是 Gin：**

1. **你要学的就是它，且它值得学**：国内公司 Go 岗位 JD 里出现频率最高的就是 Gin，教程、面试题、踩坑文章最多，卡住了随手能搜到答案——学习期这一点比任何性能指标都重要。
2. **不偏离标准库**：Gin 基于 `net/http`，学到的 `http.Handler`、`context` 知识全部可迁移。**这就是不选 Fiber 的原因**——Fiber 基于 fasthttp，API 完全不同，很多标准库中间件（如 pprof、第三方 SDK）不能直接用，学了 Fiber 换项目要重学。
3. **中间件模型简单**：`r.Use(A, B)` 洋葱模型，十分钟看懂，自己写 JWT 鉴权、限流中间件是极好的练手题。
4. **不选 Echo 的原因**：Echo 并不差，但两者能力重叠 95%，而 Gin 社区规模是它的数倍。二选一时选资料多的。
5. **性能不是问题**：Gin 用 radix tree 路由 + `sync.Pool` 复用 context，单机几万 QPS 无压力。你的瓶颈永远先出现在数据库和音频转码，不在框架。

## 2. 数据库：PostgreSQL（MySQL 也完全可以）

**候选：PostgreSQL / MySQL / SQLite / MongoDB**

**为什么是关系型数据库而不是 MongoDB：**
音乐站的数据是强关系的——用户→作品→评论→点赞→收藏夹→标签，天然是外键关联和 JOIN。
MongoDB 适合 schema 不固定的文档，这里没这个需求；而且学习期最值得练的就是 SQL 本身。

**PostgreSQL vs MySQL：**

| | PostgreSQL ✅ | MySQL |
|---|---|---|
| JSONB 字段 | 原生、可建索引 | JSON 类型较弱 |
| 全文搜索 | 内置（够早期用，省一个 Elasticsearch） | 弱 |
| 数组类型 | 有（存标签很方便） | 无 |
| 中文资料 | 中等 | 最多 |
| 招聘市场 | 上升中 | 国内主流 |

选 PostgreSQL 的关键理由是**音频元数据**：波形峰值、编辑器工程文件（轨道/剪辑点/效果参数）这类结构，用 JSONB 存最合适，将来还能对里面的字段建索引查询。MySQL 也能做，只是 JSON 能力弱一截。

> 如果你的目标是国内找工作，MySQL 资料和岗位更多，换成 MySQL 只需改一行驱动，本项目代码层面无差别。**这一条没有标准答案，两个都对。**

**ORM：GORM（同时要求自己会写裸 SQL）**

- 候选：GORM / sqlx / ent / database/sql
- 选 GORM：中文文档官方维护（gorm.io/zh_CN），CRUD 场景省大量样板代码，学习期最快出活。
- 不选 ent（entgo）：Facebook 出品，代码生成式，很优雅但概念多，适合第二个项目。
- **重要习惯**：复杂查询（排行榜、聚合统计）不要硬用 GORM 链式调用拼，直接 `db.Raw("SELECT ...")` 写 SQL。ORM 是省字的工具，不是逃避 SQL 的借口——面试考的是 SQL 和索引，不是 GORM API。

## 3. 缓存：Redis

没有候选之争，这个位置就是 Redis。用途按优先级：

1. **Session/Token 黑名单**（登出、封禁立即生效）
2. **热点缓存**：首页推荐流、作品详情页（缓存 30s 就能挡掉 90% 的 DB 读）
3. **计数器**：播放量、点赞数用 `INCR` 累积，定时批量刷回 PostgreSQL（不要每次播放都写数据库）
4. **排行榜**：`ZSET` 天然就是排行榜，`ZINCRBY + ZREVRANGE` 两条命令搞定周榜

客户端选 `go-redis/v9`（官方推荐，支持连接池、pipeline）。

## 4. 音频文件存储：MinIO（S3 协议对象存储）

**候选：存数据库 / 存本地磁盘 / 对象存储**

- ❌ 存数据库 BLOB：一首无损 50MB，数据库很快被拖垮，备份变噩梦。数据库只存**元数据和文件的 URL**。
- ❌ 直接存本地目录：起步可以，但换机器/加机器就废，且无法直接生成带过期时间的下载链接。
- ✅ **MinIO**：开源、单二进制启动、**完全兼容 AWS S3 API**。本地开发用 MinIO，上线换阿里云 OSS / 腾讯 COS / AWS S3 时**代码一行不改**（都是 S3 协议）。这是「本地开发环境与云端一致」的标准做法。

上传流程（核心思想，比代码重要）：

```
客户端 → POST /api/tracks 拿到预签名 URL（presigned URL）
客户端 → 直接 PUT 音频到 MinIO（不经过 Go 服务器，省掉一倍带宽）
客户端 → POST /api/tracks/:id/complete 通知服务端
服务端 → 丢一个转码任务到队列（见第 5 节）
```

## 5. 音频处理：FFmpeg + 内嵌任务队列 asynq

**这是本项目和普通 CRUD 网站最大的区别，也是最有含金量的部分。**

上传的音频要做三件事，全部交给 FFmpeg（不要找 Go 原生音频库，没有能打的，FFmpeg 就是行业标准）：

1. **转码统一格式**：用户传什么都转成 AAC/128k（播放用）+ 保留原文件（下载用）
2. **提取波形峰值**：把音频降采样成几百~几千个振幅值存 JSONB —— **这就是可视化的数据源**，前端拿到峰值数组直接画 Canvas，不需要在浏览器里解码整个音频
3. **读取时长/码率等元数据**：用 ffprobe

**为什么需要任务队列**：转码一首歌要几秒到几十秒，绝不能在 HTTP 请求里同步做（用户等超时）。

| 方案 | 评价 |
|---|---|
| 裸 `go func()` | 最简单，但进程重启任务就丢了，无重试 |
| **asynq** ✅ | 基于 Redis 的 Go 任务队列，有重试/延迟/优先级/Web 监控面板，学习成本一天 |
| Kafka / RabbitMQ | 杀鸡用牛刀，多维护一个重型组件 |

选 asynq 的理由：**复用已有的 Redis**，不引入新组件；API 是 Go 风格的（handler 注册模式和 Gin 神似）；将来量大了再换 Kafka，业务代码只改投递那一层。

## 6. 目录结构（Go 社区标准布局的简化版）

```
wavehub/
├── cmd/server/main.go        # 入口：只做组装（读配置→连DB→起路由）
├── internal/                 # internal 是 Go 关键字级约定：外部包无法 import
│   ├── config/               # 配置加载（环境变量）
│   ├── model/                # GORM 模型 = 数据库表结构
│   ├── handler/              # HTTP 层：解析请求、调 service、拼响应
│   ├── service/              # 业务逻辑层：核心规则都在这（含音频处理）
│   ├── middleware/           # JWT 鉴权、日志、限流
│   └── router/               # 路由注册
├── docker-compose.yml        # 一条命令拉起 PostgreSQL+Redis+MinIO
└── go.mod
```

**为什么分 handler / service / model 三层**：handler 只管 HTTP（换成 gRPC 时 service 不用动），service 只管业务（写单元测试不需要起 HTTP），model 只管表结构。这是无数项目验证过的最小分层，再多（repository 层、DTO 层）对当前规模是过度设计。

## 7. 前端方向（只给方向，本仓库先专注后端）

音乐编辑器和可视化的**重活其实在前端**，后端负责存储和转码：

- **可视化播放页**：后端存好的峰值数组 + `<canvas>` 手绘，或直接用 **wavesurfer.js**（开箱即用的波形播放器）
- **音乐编辑器**：浏览器 **Web Audio API** 是根基（AudioContext、AnalyserNode 做实时频谱），**Tone.js** 封装了合成器/效果器/时间线，是做编辑器的首选库
- 框架：Vue 3（中文资料最多）或 React 均可
- 关键分工原则：**实时的编辑和渲染在浏览器做（Web Audio API），持久化的转码和峰值提取在服务端做（FFmpeg）**——工程文件（轨道、剪辑点）以 JSON 存到 PostgreSQL 的 JSONB 字段

## 8. 一张图总结

```
浏览器 (Vue/React + Web Audio API + wavesurfer.js)
   │ HTTPS/JSON                │ 直传音频 (S3 presigned URL)
   ▼                           ▼
 Gin 单体服务  ──────────►  MinIO (音频文件)
   │        │
   │        └─► asynq 投递转码任务 ──► worker: FFmpeg 转码+提峰值
   ▼
 PostgreSQL (元数据/JSONB波形/工程文件)   Redis (缓存/计数/排行榜/队列)
```
